# 玩法实现（代码结构与数值映射）

> 本文件回答"设定里的每条规则落在哪段代码里"。
> 规则本身见 [`游戏设定.md`](游戏设定.md)；分层与插件纪律见 [`分层与命令驱动.md`](分层与命令驱动.md)。

---

## 一、总览：客户端与服务端如何分工

```
玩家操作 ─▶ 面板（Dispatch）─▶ UiInput 插件 ─▶ 领域插件构造协议体 ─▶ Run 插件
                                                                      │  POST /api/run/action
                                                                      ▼
                                                          服务器 ExecuteAction
                                                                      │
                                        现金流 / 订单 / 员工 / 市场 / 争执 各自的 handler
                                                                      │
                                               写回 State ─▶ 客户端快照 ─▶ 事件总线 ─▶ 面板刷新
```

**服务器是唯一权威**：所有数值判定（够不够钱、能不能接单、吵架谁赢）都在服务器。
客户端插件只做两件事：把入口键翻译成协议体、把服务器下发的快照投影给面板。

## 二、服务端玩法插件

目录：`Server/gameplay/plugins/`（`_` 开头的文件不是插件，只作共用模块）

| 文件 | 域 | 注册的目录域 | 行动 |
|---|---|---|---|
| `_studio.py` | **共用状态契约**（非插件） | — | — |
| `studio.py` | 门店 / 现金流 / 场地 / 设施 / 定价 | `resource` `facility` `level` `pricing` `brand` `grid` `economy` | `SetPrice` `UpgradeFacility` `ExpandStudio` `NextDay` |
| `orders.py` | 订单与拍摄 | `order` `customer_tone` `package` | `TakeOrder` `ShootOrder` `DeliverOrder` |
| `staff.py` | 员工与排班 | `staff` `trait` `staff_error` | `HireStaff` `FireStaff` `TrainStaff` |
| `market.py` | 广告 / 线上 / 品牌 / AI 冲击 | `channel` `ai_stage` `ai_cost` `ai_weakness` `route` `content_topic` | `RunAd` `PublishContent` `AdoptAI` |
| `incidents.py` | 争执 / 锐评 / 客服 | `quarrel_hand` `quarrel_customer` `reviewer` `review_tier` `service_event` | `StartQuarrel` `QuarrelMove` `SubmitReview` `ResolveServiceEvent` |
| `random_events.py` | 环境随机事件（跨系统） | — | —（只注册事件） |

合计 **17 个 ActionType、23 个目录域、18 个随机事件、2 个结局**，全部由 `Server/verify_action_contract.py`
与 `Server/verify_plugin_arch.py` 机器校验。

### 2.1 `_studio.py`：为什么要有"共用状态契约"

插件纪律是「插件之间禁止直接引用」。但纯数值玩法不可能把状态切成 5 份互不相干的数据——
现金、口碑、粉丝、订单、员工、品牌调性本来就是同一张经营报表上的列。

于是把**状态读写**抽成 `_studio.py`（以 `_` 开头，`DiscoverPlugins()` 会跳过，**它不是插件**）：

- **状态键的唯一来源**：`K_REPUTATION` / `K_ORDERS` / `K_STAFF` / `K_QUARREL` …
- **基础读写**：`Cash` / `AddCash` / `SpendCash` / `AddCashSigned` / `Reputation` / `AddReputation` / `Fans` / `Day` …
- **现金流两条腿**：`FixedCostPerDay` / `VarCostPerDay` / `AdSpendPerDay` / `CashflowState`
- **跨域操作契约**（第八节）：`AppendAppointments` / `ClearAppointments` / `AdjustAllStaffMood` /
  `WeakenStaffLoyalty` / `RequirementMissing` / `PickOrderType` / `QuotePrice`

> 为什么跨域操作也算"契约"：现实里确实存在跨域动作（线上老客带来自然客流要往订单池里塞单、
> 停电要清预约池、竞对挖人要动员工忠诚）。收进 `_studio` 之后各插件彼此**零 import**：
> 删掉 `market.py` 不会让 `orders.py` 挂，反之亦然。

**现金的单一存储位置是 `State["Resources"]["cash"]`**，没有再另存一个 `St["Cash"]`——
一条配置只有一个写入源。玩家开销一律走 `SpendCash`（余额不足直接拒绝），
只有每日结算走 `AddCashSigned`（允许扣成负数，这正是破产的来源）。

### 2.2 一天怎么走（与基座回合机制的对应）

`Round` = **已经结束营业的天数**；「当前第几天」= `Round + 1`（`_studio.Day`）。
于是**不需要额外的 `Day` 字段**，也不会出现两份天数互相漂移。

玩家点「结束营业」→ 行动 `NextDay` → `rounds.ResolveRound(St)`：

```
Round +1
  ├─ order=10  orders.DailyIntake      结清昨日预约与逾期 → 重算时段上限 → 生成今日预约池
  ├─ order=20  staff.DailyStaffCheck   每名员工一次出错判定（迟到/拍废/说错话/丢东西/吵架）
  │                                    士气衰减 + 离职风险
  ├─ order=30  market.DailyMarket      线上自然客流 / 广告转化 / AI 阶段推进 / 不可替代度净差
  ├─ order=40  incidents.DailyIncidents 锐评日提醒 + 挂一条客服事件
  ├─ order=100 studio.DailySettle      ★ 现金流结算（收入 − 固定 − 变动 → 现金 → DailyReport）
  ├─ 结束条件：studio.EndWhenBankrupt  现金 < 0 且连续 7 天净现金流为负 → 破产
  └─ 随机事件：按 GP_EVENT_CHANCE（默认 0.25）抽 1 个执行
```

**现金流结算必须是 `order=100`（最后一个）**：订单交付、工资、广告费、随机事件都会在当天改动
收入/支出/现金，早跑一步就是"报表与现状对不上"，而且这种错位极难复现。

**节奏参数**：`core.py` 默认 `TOTAL_ROUNDS = 3650`（十年）、`MATCH_HOURS = 87600`
⇒ 每回合 24 小时现实时间，即"离线一天 = 游戏一天"，天数推进完全由玩家驱动，不会在会话内乱跳。
覆盖方式：环境变量 `GP_TOTAL_ROUNDS` / `GP_MATCH_HOURS`。

### 2.3 确定性随机（为什么不用 `random`）

本作有**离线推进**（玩家不在线时服务器照样把天数走完）。若用真随机，同一份存档在不同时刻
读出来会得到不同的历史——那等于存档不可复现，排查事故时无从比对。

因此员工出错、候选人属性、订单类型抽取都用"由存档字段推出来的"确定性伪随机
（`staff._Roll` / `_RollFloat`、`_studio.PickOrderType` 的 LCG）。**只有随机事件库**用
`random`（它就是"随机事件"，不可复现是它的语义）。

### 2.4 前置条件：客服事件为什么能"模态"住所有行动

设定 8.3 要求「事件用弹窗，必须处理才能继续」。实现方式是**行动前置条件**
（`incidents.GuardServiceEvent` + `actions.RegisterPrecondition`），不是 UI 提醒：

- 有待处理客服事件时，除 `ResolveServiceEvent` / `StartQuarrel` / `QuarrelMove` 外一律拒绝；
- 写成前置条件的好处：**命令驱动路径（无 UI）遵守同一条规则**，不依赖界面自觉；
- 锁死风险已排除：每条客服事件都至少有一个 0 成本或正收益的选项，玩家不会因为没钱而被卡住。

### 2.5 「只派你能接的活」

`_studio.RequirementMissing` 是订单解锁条件的唯一实现处，被两处共用：

1. `PickOrderType` 生成预约时过滤 —— 开局不会派来"需要网红场景""需要化妆师"的活；
2. `HandleTakeOrder` 接单校验 —— 给出手把手的失败原因。

两边各写一遍就会漂移成"客人来了却接不了"，那是难度错觉，其实是 bug。

## 三、客户端玩法插件

目录：`Client/Assets/Scripts/Kitchen/Plugins/`（与服务器插件一一对应）

| 目录 | PluginId | 服务接口 | 广播事件 | 出口行动 |
|---|---|---|---|---|
| `Studio/` | `Studio` | `IStudioService` | `Studio.Changed` | setPrice / upgradeFacility / expandStudio / nextDay |
| `Orders/` | `Orders` | `IOrdersService` | `Orders.Changed` | takeOrder / shootOrder / deliverOrder |
| `Staff/` | `Staff` | `IStaffService` | `Staff.Changed` | hireStaff / fireStaff / trainStaff |
| `Market/` | `Market` | `IMarketService` | `Market.Changed` | runAd / publishContent / adoptAI |
| `Incidents/` | `Incidents` | `IIncidentsService` | `Incidents.Changed` | startQuarrel / quarrelMove / submitReview / resolveServiceEvent |

加上框架的 6 个（Health / Text / Account / Session / Run / UiInput）= **11 个插件**，
`KitchenPluginCatalog.All()` 与实现数由 `verify_plugin_arch.py --client ../Client` 核对（C1）。

### 3.1 客户端插件的固定套路（四段）

```csharp
public override void OnLoad(KitchenPluginContext ctx)
{
    m_ctx = ctx;
    ctx.RegisterService<IXxxService>(ServiceName, new XxxServiceImpl(this));   // ① 注册服务
    ctx.Subscribe<JObject>(KitchenEvents.RUN_CHANGED, OnRunChanged);           // ② 订阅单局状态
    ctx.RegisterAction(KitchenUiAction.SomeKey, action =>                      // ③ 注册行动（协议知识在这）
        KitchenActionRegistry.Body(KitchenActionType.SomeAction, "Field", action.Option));
}

private void OnRunChanged(JObject runState)                                    // ④ 摘字段 + 广播本域事件
{
    m_state = Project(runState);
    if (m_ctx != null) { m_ctx.Emit(KitchenEvents.XXX_CHANGED, m_state); }
}
```

**投影而不是转发**：每个插件只摘出本域字段（Studio 摘 `Resources`/`DailyReport`/`Facilities`…，
Orders 摘 `Appointments`/`Orders`…）。这样订阅方不必知道"门店数据散在单局状态的哪几个顶层键里"。

### 3.2 服务接口为什么只有查询、没有操作

`IStudioService` / `IOrdersService` … 一律**只提供只读查询**，改动类操作统一走
`KitchenServices.UiInput.Dispatch(UiAction.Create(...))`。

原因：给每个行动各写一个包装方法 = **第二份协议知识**。面板调服务方法、命令调 UiAction，
两条路各写一遍字段，迟早漂移。现在只有一条路（Dispatch），协议字段只在各插件的
`RegisterAction` 里出现一次。

### 3.3 `KitchenSnapshot`：安全读快照

`Kitchen/PluginFramework/KitchenSnapshot.cs` 是 5 个玩法插件共用的读取工具。
此前每个插件各写一套 `token != null && token.Type == JTokenType.Object ? ... : null`，
"取不到"的处理五花八门（有的抛异常把界面带崩，有的返回 0 让人误以为服务器数据就是 0）。
现在统一为"取不到就给调用方指定的默认值，且永不抛异常"。

### 3.4 `UiAction` 的字段纪律

`UiAction` 是全工程唯一的"操作参数包"。本作新增了 5 个公开字段：

| 字段 | 用途 |
|---|---|
| `Option` | **选择项 id**：定价档位 / 岗位 / 广告渠道 / 内容话题 / 手牌 / 顾客类型 / 锐评师 / 扩张方向 / 客服处理方式 / 附加销售 |
| `Composition` / `Timing` / `Sharpness` | 拍摄微操三轴（0~1） |
| `Retouch` | 后期修图强度（0~1） |

其余（目标对象 id / 员工号 / 订单号 / 预约号）复用已有的 `TargetId`，不另开字段。

> ⚠ 硬性要求：**每新增一个公开字段，必须同步加进 `KitchenCommandRunner.s_setters`**，
> 否则"这条命令没法用脚本表达"，要等到回归时才发现。5 个字段都已登记。

**拍摄微操的 0 值语义**：三轴全为 0 表示"跳过微操，按员工技能自动结算"。这条语义只在
`OrdersPlugin` 的 `RegisterAction` 里出现一次——面板漏传一个参数就会变成"玩家手抖得 0 分"，
所以必须有唯一权威。

## 四、状态契约（单局快照字段表）

`_studio.EnsureFields` 在 `NewState`（`RegisterInitializer`，order=5）与旧档清洗
（`RegisterSanitizer`）时都会跑，是**所有玩法字段的唯一补全点**。

| 键 | 类型 | 含义 |
|---|---|---|
| `Round` | int | 已结束营业的天数（基座字段）；当前第几天 = Round + 1 |
| `Resources` | dict | `cash` / `film` / `inspiration` / `skill` |
| `Facilities` | dict | 13 项场地分区与设备的等级（1~5） |
| `Grid` | dict | `{W, H, Expanded}`，初始 6×8 |
| `Reputation` | float | 口碑星级 0~5 |
| `Fans` | int | 线上粉丝 |
| `BrandScore` | dict | 品牌调性积分，当前调性 = argmax |
| `PriceTier` | str | 当前定价档位 id（`pricing` 目录） |
| `Appointments` | list | 今日预约池（未接） |
| `LostToday` | int | 今日流失预约数 |
| `TotalSlots` | int | 今日可用时段上限 |
| `Orders` | list | 订单（`State`: booked / shot / delivered） |
| `Staff` | list | 员工（Id / Post / Skill / Speed / Mood / Loyalty / Trait / Wage） |
| `Ads` | list | 今日已投放渠道 id |
| `AI` | dict | `{Stage: 0~4, Subscribed: bool}` |
| `Irreplaceable` | int | 不可替代度 |
| `ReplacePower` | int | AI 替代能力（服务器每日重算） |
| `IncomeToday` / `FixedCostToday` / `VarCostToday` | int | 当日流水（结算后清零） |
| `DailyReport` | dict | 最近一天的日报表（客户端直接渲染） |
| `NegativeDays` | int | 连续净现金流为负的天数（破产判定用） |
| `Quarrel` | dict / null | 进行中的论战 |
| `QuarrelsToday` | int | 今日已吵场次（上限 2） |
| `ServiceEvent` | dict / null | 待处理的客服事件（模态） |
| `ReviewHistory` | list | 锐评历史 |
| `ReviewDoneRound` | int | 最近一次锐评投稿的回合 |
| `PublishedRound` | int | 最近一次发内容的回合（每天限 1 条） |
| `TimedEffects` | dict | 持续效果 → 到期天数 |
| `RentMult` / `ExposureMult` / `OutdoorMult` | float | 房租 / 线上曝光 / 外拍效率倍率 |
| `OrderSeq` / `StaffSeq` | int | 订单号 / 员工号自增游标 |

> 协议字段名是**兼容红线**：改名等于改存档格式。新增字段必须走 `EnsureFields`
> （旧档才能补上默认值），不要散在插件里 `St.setdefault`。

## 五、关键数值与调参入口

| 数值 | 位置 | 默认值 |
|---|---|---|
| 开局现金 | `studio._RESOURCES` 的 `cash.start` | 10,000 |
| 开局口碑 | `studio._ECONOMY` 的 `initialReputation` | 2.0 |
| 房租 / 格 / 天 | `studio._ECONOMY.rentPerCell` | 2.5 |
| 物业水电 / 格 / 天 | `studio._ECONOMY.utilityPerCell` | 0.8 |
| 设备日折旧率 | `studio._ECONOMY.depreciationPerDay` | 0.006 |
| 破产判定天数 | `_studio.BANKRUPT_NEGATIVE_DAYS` | 7 |
| 现金流状态阈值 | `_studio.HEALTHY_DAYS` / `TIGHT_DAYS` | 30 / 7 |
| 每天时段数 | `_studio.SlotsPerDay` | 8 +（接待区等级 − 1）|
| 每天发内容条数 | `incidents` 之外，`market.HandlePublishContent` | 1 |
| 每天吵架次数 | `incidents.MAX_QUARRELS_PER_DAY` | 2 |
| 吵架回合上限 | `incidents.QUARREL_MAX_ROUNDS` | 5 |
| 客服事件频率 | `incidents.SERVICE_EVENT_EVERY_DAYS` | 每 3 天 |
| 随机事件概率 | 环境变量 `GP_EVENT_CHANCE` | 0.25 |
| AI 阶段分界 | `market._AI_STAGES[].minDay` | 1 / 30 / 60 / 120 / 180 |

> **一条配置只有一个存储源**：所有目录条目（订单价、岗位日薪、渠道成本、定价系数…）
> 都只在对应的 `Server/gameplay/plugins/*.py` 里写一遍，客户端通过 `/api/catalog` 取。
> 客户端**不硬编码任何经营数值**。

## 七、扩展点（本版本没做，接口已经留好）
