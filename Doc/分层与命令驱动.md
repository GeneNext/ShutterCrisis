# 分层与命令驱动

本文定义 `ShutterCrisis` 客户端的三层结构、每层能做什么 / 不能做什么、服务门面与事件总线的唯一通道，以及“命令驱动”如何保证 UI 能做的命令也能做。

> 适用范围：客户端 `Client/Assets/Scripts/`；服务端插件结构见 [`服务器基座.md`](服务器基座.md)。  
> 硬约束：**数据层跑数据层、UI 层跑 UI 层，两层只经管理器与控制器交互；游戏必须能用命令执行。**

## 一、三层总览

| 层 | 实际目录 | 当前主文件 | 职责 | 不能做 |
| :--- | :--- | :--- | :--- | :--- |
| 数据层 | `Client/Assets/Scripts/Kitchen/**` | `PluginFramework/`、`Plugins/`、`Command/KitchenCommandRunner.cs` | 插件生命周期、服务、协议字段知识、目录、事件总线、行动注册表、命令执行器 | 不引用 UI；不持有共享 `State` 字典 |
| 管理层 | `Client/Assets/Scripts/UI/Kitchen/*.cs` | `KitchenServices.cs`、`KitchenClientBootstrap.cs`、`Session/SessionReporter.cs`（目标还包含场景路由 / 地图模块 / 面板导航） | 服务门面、场景跳转、会话上报、组合根、面板管理器 | 不做业务判定；不复制数据层规则 |
| 面板层 | `Client/Assets/Scripts/UI/Panels/**`（由一键生成产出） | 生成的 `XxxPanelView` / `XxxPanelModel` / `XxxPanelController` | 把状态画出来、把意图交出去、订阅事件刷新 | 不直连数据层、不 `new XxxPlugin(...)`、不自己拼协议 Body、不解析服务器字段 |

> 判断一个文件属于哪一层：看它是否具备“无 UI 也能跑”的能力。数据层完全可以；管理层编排数据层但依赖 Unity 对象；面板层离开 Unity 场景就没有意义。

### 1.1 当前迁移状态

- `UI/Kitchen/` 当前有 `KitchenClientBootstrap.cs`、`KitchenServices.cs`、`Session/SessionReporter.cs` 与 `README.md`；场景路由 / 地图模块不在基座默认范围内，按项目需要自行补。
- `UI/Panels/` 目录当前尚未生成面板 MVC 文件；面板由 `UI/Editor/KitchenUIGenerationPipeline.cs` 在“一键生成”时产出。
- `KitchenServices.cs` 当前登记 11 个服务：框架 6 个（Health / Account / Session / Text / Run / UiInput）
  + 玩法 5 个（`Studio` / `Orders` / `Staff` / `Market` / `Incidents`）。新增域服务 = 插件里
  `ctx.RegisterService<T>(ServiceName, impl)` + 本文件加一个只读属性，面板**只认门面**。
- `KitchenPluginCatalog.All()` 与 `Kitchen/Plugins/` 下的 11 个实现一致；
  `verify_plugin_arch.py --client ../Client` 通过（8 项 / 0 失败）。仍待补的功能性缺口是
  `PanelManager.Back()`、`SimpleButton.SetInteractable/SetVisible` 与 `AssetCdnConfig.asset` 的占位地址。

## 二、每层职责与禁止事项

### 2.1 数据层（Kitchen）

**放什么**

- `Kitchen/PluginFramework/`：`KitchenPluginEngine`、`KitchenEventBus`、`KitchenPluginContext`、`KitchenPlugin`、`KitchenPluginBase`、`KitchenPluginCatalog`、`KitchenPluginRuntime`、`KitchenActionRegistry`、`KitchenActionType`、`KitchenEvents`、`KitchenServiceKeys`。
- `Kitchen/Plugins/<域>/`：每个域一个插件，通常包含 `XxxPlugin.cs` + `XxxService.cs`；协议字段知识只放在这里。
- `Kitchen/Command/KitchenCommandRunner.cs`：命令行入口。
- 目录 / 状态读取器：从服务器下发快照中取数，但不复制玩法规则。
- 地图场景契约：`IMapSceneService` 等（若新项目需要地图能力）。

**禁止**

- `using` 任何 `ShutterCrisis.UI` 命名空间或 UI 类型。
- 直接订阅 `KitchenEventBus` 而不经 `KitchenPluginContext.Subscribe`（后者保证卸载时统一退订）。
- 插件之间直接 `new` 或强引用；需要协作时发事件或取服务接口。
- 把服务器下发的 `JObject` 当成本地可变对象改写后广播。
- 维护共享 `State` 字典（历史事故：多个插件读写同一份裸状态，调用方无法知道谁改了值）。

### 2.2 管理层（UI/Kitchen）

**放什么**

- `KitchenServices.cs`：面板访问插件服务与事件总线的唯一入口。
- `KitchenClientBootstrap.cs`：组合根，负责启动热更、加载目录、调用 `KitchenPluginRuntime.Build()`、打开首个面板。
- `SessionReporter.cs`：面板开关 / 行动 / 场景上下文上报。
- 场景路由、面板导航规则、地图服务门面（目标结构，当前仍在迁移）。

**禁止**

- 在管理层写玩法判定；判定在服务器。
- 让面板直接持有 `KitchenPluginEngine` / `KitchenPluginContext`。
- 把“装配哪些插件”的知识留在 UI（目标：装配知识归 `KitchenPluginCatalog` + `KitchenPluginRuntime`）。

### 2.3 面板层（UI/Panels）

**合法写法**

- 取数：`KitchenServices.<域属性>` 或 `KitchenServices.Get<T>(ServiceName)`。
- 跳转：`PanelManager.OpenPanel` / `ClosePanel`（目标还有 `Back()`）。
- 刷新：订阅 `KitchenEvents.*` 常量事件。
- 行动：只表达意图，调用服务方法或 `IUiInputService.Dispatch`。

**禁止**

- `new XxxPlugin(...)`。
- 取 `KitchenPluginContext` / `KitchenPluginEngine`。
- 自己拼协议 Body。
- 自己解析服务器字段（例如遍历服务器状态对象取嵌套字段）。
- 直接读地图数据表、面板跳转表之外的“第二份事实源”。

## 三、服务门面与 `KitchenServiceKeys`

### 3.1 面板取服务的唯一入口

当前文件：`Client/Assets/Scripts/UI/Kitchen/KitchenServices.cs`。

写法：

```csharp
// 约定键：接口名去掉前导 I、去掉后缀 Service
IRunService run = KitchenServices.Run;
IUiInputService input = KitchenServices.UiInput;

// 显式键：一个接口多个实例时必须用（例如多张地图各有一个服务实例）
IMapSceneService world = KitchenServices.Get<IMapSceneService>("WorldMapScene");
```

目标是面板只依赖 `KitchenServices`（或 `ShutterCrisisServices`），不要直接写：

```csharp
KitchenClientBootstrap.Engine.GetService<IRunService>("Run"); // 禁止：面板与引导类硬绑死
```

### 3.2 `KitchenServiceKeys` 的键推导

文件：`Client/Assets/Scripts/Kitchen/PluginFramework/KitchenServiceKeys.cs`。

规则：

1. 取接口类型名。
2. 若首字符是 `I` 且第二个字符大写，去掉 `I`。
3. 若以 `Service` 结尾，去掉 `Service`。

示例：

| 接口 | 约定键 |
| :--- | :--- |
| `IRunService` | `Run` |
| `IUiInputService` | `UiInput` |
| `IMapService` | `Map` |

例外：一个接口有多个实例时，键无法由类型唯一确定，必须显式传各自插件的 `ServiceName`。例如多张地图场景各自注册 `IMapSceneService` 时，不能只靠 `GetService<IMapSceneService>()`。

### 3.3 服务注册与回收

插件在 `OnLoad` 里注册：

```csharp
public void OnLoad(KitchenPluginContext ctx)
{
    ctx.RegisterService<IMyService>(MyPlugin.ServiceName, new MyService());
    ctx.Subscribe(KitchenEvents.RUN_CHANGED, OnRunChanged);
    ctx.RegisterAction(KitchenUiAction.DoThing, BuildDoThingBody);
}
```

`KitchenPluginContext` 在 `Dispose()` 时统一：

- 逆序退订本插件注册的事件订阅；
- 逆序注销本插件注册的服务；
- 不暴露裸 `Services` / `State` 字典给插件。

## 四、事件总线：唯一通信通道

### 4.1 事件名必须集中声明

文件：`Client/Assets/Scripts/Kitchen/PluginFramework/KitchenEvents.cs`。

规则：

- 事件名必须是 `KitchenEvents` 中的 `public const string`。
- 禁止在业务代码里 `Emit("Run.Changed")` / `Subscribe("Run.Changed")` 这类裸字符串。
- 事件负载一律是**快照**：自定义状态用 `Copy()`；服务器下发对象视为只读。
- 同一个事件名不能挂两种负载类型；出现形态变化时新增事件名，不要复用旧名。

### 4.2 插件侧订阅

插件内统一通过 `KitchenPluginContext`：

```csharp
ctx.Subscribe<RunChangedPayload>(KitchenEvents.RUN_CHANGED, OnRunChanged);
```

优点：`OnUnload` 后框架统一退订；订阅来源记录为插件 Id，诊断窗口能回答“谁在听什么”。

### 4.3 UI 侧订阅

面板 / 控制器统一通过 `KitchenServices`：

```csharp
KitchenServices.Subscribe(KitchenEvents.RUN_CHANGED, OnRunChanged);
```

`Subscribe` / `Unsubscribe` 必须成对；推荐使用可 `Dispose` 的订阅句柄，或在 `UnregisterEvent_View` 中显式退订。事件总线已做“同一目标 + 同一方法 + 同一来源”的幂等去重，但退订纪律仍是调用方责任。

### 4.4 插件互不引用

- 插件间协作只允许：事件总线、服务接口。
- 不允许 `new OtherPlugin()`、不允许直接调用另一个插件的静态方法、不允许持有另一个插件的具体类型字段。
- 依赖关系用 `IKitchenPlugin.Dependencies` 声明；引擎在 Load 前做拓扑排序，缺依赖或成环直接抛异常。

## 五、命令驱动：`命令 [字段=值 ...]`

### 5.1 入口与格式

文件：`Client/Assets/Scripts/Kitchen/Command/KitchenCommandRunner.cs`。

格式：

```text
命令 [字段=值 ...]
```

规则：

- 空白分隔；值含空格时用双引号包裹。
- 无 `=` 的 token 被忽略（命令本身已表达意图）。
- 未知字段直接报错，不静默丢弃。
- 命令名大小写由 `KitchenActionRegistry` 的注册键决定；参数名大小写不敏感（`StringComparer.OrdinalIgnoreCase`）。

示例（本作真实命令；字段名与 `UiAction` 公开字段一一对应）：

```text
start
refresh
settle Force=true
setPrice Option=midhigh
upgradeFacility TargetId=studio
expandStudio Option=right
nextDay
takeOrder TargetId=12
shootOrder TargetId=12 Composition=0.9 Timing=0.8 Sharpness=0.7
deliverOrder TargetId=12 Retouch=0.5 Option=reprint
hireStaff Option=photographer
trainStaff TargetId=3
runAd Option=douyin
publishContent Option=before_after
adoptAI Force=true
startQuarrel Option=tough
quarrelMove Option=fact
submitReview Option=gentle
resolveServiceEvent Option=reshoot
```

> 这一整串正是"UI 能做的 = 命令能做的"的验收方式：
> 在没有打开任何面板的情况下，这些命令就能把一局经营从第 1 天推到破产。

### 5.2 与 UI 同一条路径

```text
UI 按钮 ─┐
         ├─> IUiInputService.Dispatch(UiAction)
命令行 ──┘        ├─> KitchenActionRegistry.TryExecute（流程命令）
                  └─> KitchenActionRegistry.Build（行动体）→ 服务方法 / Run.Action
```

因此：

- `KitchenCommandRunner.Execute(engine, commandLine, callback)` 与 UI 按钮完全同路。
- `KitchenCommandRunner.Commands(engine)` 返回全部可执行命令。
- `KitchenCommandRunner.ArgumentNames()` 返回参数名全集。
- `KitchenCommandRunner.IsKnown(engine, commandLine)` 供脚本预检，避免拼错命令却以为执行了。

### 5.3 `UiAction` 字段必须全部可表达

`KitchenCommandRunner` 内部维护 `UiAction` 公开字段到命令行参数的映射表。规则：

- `UiAction` 新增任何公开字段，必须同步在该映射表中加一行。
- 否则会出现“命令无法表达某个动作”，自动化回归覆盖不到。
- 机器门禁的对应检查应确认“映射表覆盖全部 `UiAction` 公开字段”（源工程有该规则；当前基座脚本见第六节）。

### 5.4 验收线

以下两行应能在**没有任何 Panel / View** 的情况下完成“开新局 → 配置 → 行动 → 结算”：

```csharp
KitchenPluginEngine engine = KitchenPluginRuntime.Build();
KitchenCommandRunner.Execute(engine, "start", (ok, msg) => { /* 断言 */ });
```

如果一条 UI 能完成的操作无法用命令表达，说明字段知识散落在面板或行动注册表不完整，需要回到插件层修。

## 六、机器门禁与防回潮

### 6.1 当前可运行的脚本

| 命令 | 文件 | 当前检查 |
| :--- | :--- | :--- |
| `cd Server && python verify_plugin_arch.py --client ../Client` | `Server/verify_plugin_arch.py` | S1 自动发现 ≥1 个插件且可导入；S2 ActionType 名合法 / 处理器可调用；S3 声明已进运行时；S4 插件有 docstring；S5 重复 `RegisterAll()` 幂等；S6 玩法自检全绿；C1 客户端插件实现数 == 目录清单条目数（默认布局为 `Assets/Scripts/Kitchen/Plugins` + `Kitchen/PluginFramework/KitchenPluginCatalog.cs`） |
| `cd Server && python verify_action_contract.py --client ../Client` | `Server/verify_action_contract.py` | 服务端注册表非空、无空名/重复、每个 ActionType 有处理器、插件源码 `ACTIONS` 声明均已注册；有客户端常量文件时做双向契约 |
| `cd Server && python verify_client_static.py --client ../Client` | `Server/verify_client_static.py` | `.cs` ↔ `.cs.meta` 一一对应；meta GUID 32 位且唯一；asmdef 依赖无环；asmdef 引用可解析；项目内 enum 成员引用存在 |
| `python Tools/compile_check/compile_check.py --errors-only` | `Tools/compile_check/compile_check.py` | 按 asmdef 拓扑序真编译自有程序集 |
| `python Tools/unity_check/unity_check.py --errors-only` | `Tools/unity_check/unity_check.py` | 团结引擎批处理真编译，解析 `CompilationErrors.log` |

### 6.2 目标扩展规则（源工程已有，当前基座脚本尚未全部实现）

源工程的插件化门禁还包含以下规则；迁移到新项目时建议按自己的门禁脚本补齐：

| 规则 | 守什么 |
| :--- | :--- |
| 5 | 数据层（`Kitchen/**`）不反向依赖 UI |
| 7 | 数据层无共享 `State` 字典 |
| 8 | 面板层不直读数据层内部数据表 |
| 9a | `UiAction` 全部公开字段可被命令表达 |
| 9b | 面板层只经管理层 / 控制器访问数据层 |

`Server/verify_plugin_arch.py` 的客户端规则默认布局就是 `Assets/Scripts/Kitchen/Plugins` 与
`Assets/Scripts/Kitchen/PluginFramework/KitchenPluginCatalog.cs`；加 `--client ../Client` 即可执行，
**当前 C1 通过（11 个实现 == 11 条目录）**。

`Server/verify_action_contract.py --client ../Client` 会自动探测 `KitchenActionType.cs`，
并且**只解析 `class KitchenActionType` 的字符串值**（`KitchenUiAction` 是同文件里另一组语义的常量，
混在一起会比对出假失败 —— 脚本已按类名精确取体，注释与 camelCase 入口键都不参与比对）。
**当前双向校验通过 6 项 / 0 失败（17 个 ActionType 一致）**。

### 6.3 防回潮要求

- 不新增共享 `State` 字典；插件私有状态放自己的字段。
- 不从客户端改写服务器下发的对象；只能发行动、读快照、发事件。
- 不新增裸字符串事件名 / 服务键 / ActionType；常量必须集中声明。
- 不在面板里 `new` 插件、不取插件上下文、不自己拼协议 Body。
- 新增服务必须有真实消费者（面板或另一个插件）；否则门禁的“服务消费者”规则会告警。
- 新增/修改行动字段时，先改服务端插件契约，再同步客户端常量与参数映射表，最后跑双向契约校验。

## 七、新增一个玩法插件

以下清单区分“客户端侧”和“服务器侧”；两侧的 ActionType 字符串必须一致。

### 7.1 客户端侧

1. 新建 `Client/Assets/Scripts/Kitchen/Plugins/<域>/<域>Plugin.cs`：实现 `IKitchenPlugin` 或继承 `KitchenPluginBase`；声明 `Id`、`Version`、`Dependencies`。
2. 新建 `Client/Assets/Scripts/Kitchen/Plugins/<域>/<域>Service.cs`：接口 + 实现；协议字段知识只放这里。
3. 在 `OnLoad` 中：
   - `ctx.RegisterService<IXxxService>(XxxPlugin.ServiceName, service)`；
   - 需要监听状态变化时 `ctx.Subscribe(KitchenEvents.XXX_CHANGED, handler)`；
   - 通用行动用 `ctx.RegisterAction(KitchenUiAction.Xxx, BuildXxxBody)`；
   - 流程类操作用 `ctx.RegisterCommand(KitchenUiAction.Xxx, ExecuteXxx)`。
4. 在 `Client/Assets/Scripts/Kitchen/PluginFramework/KitchenPluginCatalog.cs` 的 `All()` 中加一行 `new XxxPlugin()`。注册顺序不重要，引擎会拓扑排序。
5. 如果新增 ActionType：
   - 在 `Client/Assets/Scripts/Kitchen/PluginFramework/KitchenActionType.cs` 的 `KitchenActionType` 中加 PascalCase 常量；
   - 在 `KitchenUiAction` 中加 camelCase 入口键；
   - 如果 `UiAction` 带了新字段，在 `KitchenCommandRunner.cs` 的参数映射表中加一行。
6. 在 `Client/Assets/Scripts/UI/Kitchen/KitchenServices.cs` 中加一个域属性（如 `public static IStudioService Studio`），供面板取服务；如果该服务已有消费者，门禁的"服务必须有消费者"检查才能通过。
7. 需要新面板时，先在 `PanelMVC.xml` 登记、再到 `UI/PanelNavRule.cs` 登记分层与互斥，最后按 [`UI规范与一键生成.md`](UI规范与一键生成.md) 走"一键生成"。

### 7.2 服务器侧

1. 新建 `Server/gameplay/plugins/<域>.py`，**参考 `Server/gameplay/plugins/orders.py`**（最完整的一个域：
   目录 + 行动 + 回合钩子 + 随机事件 + 自检齐全）；只做跨域状态读写的共用逻辑放
   `Server/gameplay/plugins/_studio.py`（下划线开头，`DiscoverPlugins()` 会跳过，它不是插件）。
2. 声明可选模块级成员：
   - `PLUGIN_NAME`；
   - `ACTIONS = {"ActionType": handler}`；
   - `def Register(): ...`（注册目录 / 回合钩子 / 结算 / 事件 / 前置条件）；
   - `VERIFY = [fn]`（自检）。
3. **不要**修改 `Server/gameplay/plugins/__init__.py` 的注册清单：它使用 `pkgutil.iter_modules` 自动发现。
4. 行动处理器签名固定：

```python
def HandleXxx(St, Action, ReportLines):
    # St          单局状态 dict（直接改；服务层统一落盘）
    # Action      客户端提交的行动对象（至少含 ActionType）
    # ReportLines 本回合战报行列表（append 会随 State 回给客户端）
    return True, "ok"
```

5. 需要在客户端目录中暴露条目时，在 `Register()` 中调用 `core.RegisterDirectory("<域>", [...])`。
6. 跑 `cd Server && python -m gameplay.verify` 与 `python verify_action_contract.py`。

### 7.3 两侧共同验收

- `python Tools/compile_check/compile_check.py --errors-only` 通过。
- `cd Server && python verify_plugin_arch.py` 通过。
- `cd Server && python verify_action_contract.py` 通过（需要正确的客户端常量文件路径）。
- `cd Server && python verify_client_static.py --client ../Client` 通过。
- 如果新增面板，走完“一键生成”并确认面板能进 / 能关 / 能返回。
