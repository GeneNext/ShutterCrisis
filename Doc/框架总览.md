# 框架总览

本文是 `ShutterCrisis` 所用**框架层**的总览：它是什么、能力边界在哪里、客户端 / 服务器 / 工具链三层如何组织，以及一次玩家请求从 UI 到服务器再回到 UI 的完整链路。

> 适用范围：`E:\Projects\Game\ShutterCrisis`。本文只描述框架层机制，**不包含任何具体玩法规则**（玩法内容由本工程自己实现）。  
> 阅读顺序：先读本文建立全局图，再按需要进入 [`分层与命令驱动.md`](分层与命令驱动.md)、[`UI规范与一键生成.md`](UI规范与一键生成.md)、[`服务器基座.md`](服务器基座.md)。

## 一、框架定位与能力边界

### 1.1 这是什么

`ShutterCrisis` 的框架层由原型基座 `GamePrototype` 改名而来，用于承载本作的全部工程能力：

- Unity 客户端四层程序集：`ShutterCrisis.Framework` / `.Data` / `.Kitchen` / `.UI`。
- 客户端插件框架：生命周期驱动、服务注册、事件总线、行动注册表、命令驱动。
- 服务端 HTTP 基座：`server.py` 薄路由 + `services/` 服务层 + `gameplay/` 玩法插件包。
- 资源热更：AssetBundle 打包、AssetCache 缓存、AssetLoader 加载与清单指针下载。
- UI 一键生成：面板 MVC 脚本、Prefab、场景层骨架、占位面板、字体子集。
- 多平台接入：`PlatformService` 门面 + `IPlatform` 抽象 + 平台实现自注册。
- 文档与门禁：桩编译、真编译、静态自检、插件架构门禁、协议契约校验。

### 1.2 这不是什么

- 不是完整商业游戏：框架层本身不含玩法；具体规则由本工程的 `Kitchen/Plugins/<域>/` 与 `Server/gameplay/plugins/*.py` 提供，目前仍在填充。
- 不是第二套 UI 框架：面板必须走 `PanelManager` + BaseMVC + 一键生成，不允许另建面板系统。
- 不是客户端权威架构：玩法判定、状态变更、结算在服务器；客户端插件只发行动、读快照、发事件。
- 不是多语言内容库：界面文案最终走文案表 `Tools/text_table/` 与 `Resources/UI/Text/*.json`，框架只提供通道与字体子集工具。

### 3.2 为什么这样分

- **编译期强制依赖方向**：低层不能引用高层。`ShutterCrisis.Kitchen` 不能 `using ShutterCrisis.UI`；`ShutterCrisis.Data` 不能引用 `UI`。这比“靠代码审查”硬，违反时直接 CS0246。
- **防止插件反向依赖表现层**：插件必须能脱离 UI 跑（命令驱动、自动化回归、未来服务器侧回放）。插件若引用 UI，headless 验收不可能成立。
- **平台 SDK 隔离**：`ShutterCrisis.Framework` 不引用任何平台 SDK；每个平台实现独立 asmdef，经 `PlatformRegistry` 自注册，SDK 缺失时回退 `StandalonePlatform`。
- **编辑器公共工具独立**：`ShutterCrisis.Editor.Common` 只依赖 Framework，避免模块编辑器程序集之间形成 asmdef 环。

## 四、服务器分层

服务器是“薄路由 + 服务层 + 玩法插件包”的三层结构。

| 层 | 位置 | 职责 | 禁止 |
| :--- | :--- | :--- | :--- |
| 路由层 | `Server/server.py` | HTTP 收发、CORS、JSON 解析、请求体上限、路由分发、参数挑选、启动 HTTPServer | 写业务判定；解析具体玩法字段 |
| 服务层 | `Server/services/` | 账号 / 登录 / 存档 / 会话 / 单局生命周期 / 目录聚合 / 资源清单 / 后台 / 存储后端 | 写具体玩法数值规则；直接 `rfile` |
| 玩法插件包 | `Server/gameplay/` | 状态容器、行动分发、回合推进、结算、随机事件、插件自动发现 | 处理 HTTP；依赖 `services/` 之外的请求上下文 |

核心文件：

- `Server/server.py`：路由表、`_handle_*`、`do_GET` / `do_POST`、`BuildStore()`、`main()`。
- `Server/services/account.py`：`Store`、`LoginByCode`、`LoginByToken`、`LoginByPassword`、`Register`、`SetNickname`、`Sync`、`Save`。
- `Server/services/session.py`：`Heartbeat`、`OnlineSnapshot`、`ThrottleHeartbeat`。
- `Server/services/run.py`：`RunService`（`Start` / `State` / `Action` / `Settle`）。
- `Server/services/catalog.py`：`BuildCatalog`、`CatalogGet`。
- `Server/services/asset.py`：`AssetManifestGet`、`AssetBundleGet`、`AssetBundleSave`。
- `Server/services/admin.py`：后台管理业务函数。
- `Server/services/storage.py`：`StorageBackend`、`JsonStorageBackend`、`CreateBackend`。
- `Server/services/postgres_storage.py`：`PostgresStorageBackend`、`DDL_STATEMENTS`。
- `Server/gameplay/`：`core.py` / `state.py` / `actions.py` / `events.py` / `rounds.py` / `settle.py` / `plugins/` / `verify/`。

### 4.1 玩法插件自动发现

`Server/gameplay/plugins/__init__.py` 的 `DiscoverPlugins()` 用 `pkgutil.iter_modules` 扫描 `gameplay/plugins/` 下所有非下划线开头的 `.py` 文件并导入；`RegisterAll()` 收集每个模块的：

- `PLUGIN_NAME`：可选，展示名。
- `ACTIONS = {"ActionType": handler}`：可选，行动注册表。
- `def Register(): ...`：可选，注册目录 / 回合钩子 / 结算钩子 / 事件 / 前置条件。
- `VERIFY = [fn]`：可选，自检项，由 `gameplay/verify` 聚合执行。

**新增玩法插件不需要改任何注册清单**：复制 `Server/gameplay/plugins/orders.py` 改名即可
（它是最完整的一个域：目录 + 行动 + 回合钩子 + 事件 + 自检一应俱全）。
只做"跨域状态读写"的共用逻辑放 `plugins/_studio.py`（下划线开头，不会被当成插件）。
详见 [`服务器基座.md`](服务器基座.md) 与 [`玩法实现.md`](玩法实现.md)。

### 5.3 AssetLoader 层与热更链

| 文件 | 职责 |
| :--- | :--- |
| `Client/Assets/Scripts/AssetLoader/AssetLoader.cs` | 统一加载入口：`LoadAsset` / `LoadAssetComponentInstance` / `LoadAllAsset`；内部先查 AssetCache，再按加载模式走 Resources / AssetBundle |
| `Client/Assets/Scripts/AssetLoader/AssetLoaderData.cs` | `eAssetType` / `eFreeMemoryType` / `eAssetLoadType` / `eAssetLoadMode` 等加载枚举 |
| `Client/Assets/Scripts/AssetLoader/AssetCdnConfig.cs` | CDN 根、清单接口、下载超时 / 重试 / 并发 / md5 校验 / 首屏预下载 / 缓存目录 / 加载模式 |
| `Client/Assets/Scripts/AssetLoader/AssetManifest.cs` | `AssetManifest` / `AssetFileEntry` / `AssetUpdateCheckResult` / `AssetDownloadResult` / `eAssetUpdateState` |
| `Client/Assets/Scripts/AssetLoader/AssetBundleCache.cs` | 本地缓存目录：`current.txt` / `cache.json` / `<version>/`，版本切换与旧版本清理 |
| `Client/Assets/Scripts/AssetLoader/AssetDownloader.cs` | `UnityWebRequest` 下载 + 进度 + 重试 + md5 + 原子落盘 |
| `Client/Assets/Scripts/AssetLoader/AssetHotUpdateService.cs` | 热更总入口：取清单 → 版本比对 → 下载 → 切换版本 → 清理 → 首屏预下载 |
| `Client/Assets/Scripts/AssetLoader/AssetHotUpdateRunner.cs` | 把热更接到 Unity 生命周期，显示进度覆盖层，失败降级不阻塞启动 |
| `Client/Assets/Scripts/AssetLoader/HotUpdateOverlay.cs` | 纯代码构建的热更进度覆盖层 |

**设计原则**：

1. 业务层只调 `AssetLoader.*`，不直接调 `Resources.Load` / `AssetBundle.LoadFromFile`（引导配置 `AssetCdnConfig.Instance` 是唯一例外）。
2. 业务资源不直接写磁盘路径；平台缓存一律走 `AssetBundleCache`。
3. 热更清单优先走服务端接口 `GET /api/asset/manifest?platform=`，失败再回退直读 CDN 的 `version.json`。
4. 下载必须 md5 校验 + `.tmp` 原子替换；**全部成功才切换 `current.txt`**，避免半新半旧。
5. 失败不阻塞启动：退回本地缓存或内嵌资源，状态置 `Failed` 并记录原因。

### 5.4 当前已知缺口

- `AssetLoaderData.cs` 当前已包含 `eAssetLoadMode`（`Editor` / `LocalBundle` / `ServerBundle`），`AssetLoader.cs` 也提供了 `LoadMode` / `ClampMode` 等入口；加载模式的唯一配置源是 `AssetCdnConfig.RuntimeLoadMode`（Resources 下，编辑器与真机都读得到），`AssetBundleBuildSO.LoadMode` 已标记 `[System.Obsolete]`，不要再用它。
- `AssetCdnConfig.cs` 的代码默认 CDN 根是占位地址；`Client/Assets/Resources/GameData/AssetCdnConfig.asset`
  里仍是占位值，**真机可读、会覆盖代码默认值**，换真实 CDN 时必须替换该资产，
  见 [`新项目落地清单.md`](新项目落地清单.md) 第二节。

## 六、一次请求的完整链路

以下以"面板发起一次服务器行动"为例，用本作真实的一个行动（改定价 `SetPrice`）走完全程：

```text
[面板层]
PanelController
  └─ 只表达意图，不碰协议：
     KitchenServices.UiInput.Dispatch(UiAction.Create(KitchenUiAction.SetPrice, "midhigh"), callback)
        │
        ▼
[管理层 / 服务门面]
KitchenServices（UI/Kitchen/KitchenServices.cs）
  └─ UiInput 属性 → IUiInputService（UiInput 插件注册的服务实例）
        │
        ▼
[数据层 / 输入分发]
UiInputPlugin.Dispatch
  └─ 广播 KitchenEvents.UI_ACTION（埋点 / 会话留痕）
  └─ 查流程命令表（start / refresh / settle 等）→ 命中就执行
  └─ 否则查行动体表：StudioPlugin 注册的构造器把它翻成协议体
       KitchenActionRegistry.Body(KitchenActionType.SetPrice, "Tier", action.Option)
  └─ 交给 IRunService.Execute(body, callback)（**UI 与命令走的是同一条路**）
        │
        ▼
[网络通道]
Data/ServerCommRun.cs
  └─ POST {GameConst.ServerUrl}/run/action
        │
        ▼
[服务器路由层]
Server/server.py::_handle_run_action
  └─ 校验 token → RUN_SERVICE.Action(player_id, action)
        │
        ▼
[服务器服务层]
Server/services/run.py::RunService.Action
  └─ LoadAndAdvance（离线推进：按真实经过时间补算回合）
  └─ gameplay.ExecuteAction(state, action, report_lines)
        │
        ▼
[玩法插件层]
Server/gameplay/actions.py::ExecuteAction
  └─ 前置条件（默认"单局未结束" + 插件追加的规则，如客服事件模态拦截）
  └─ ACTIONS["SetPrice"] → plugins/studio.py::HandleSetPrice(St, Action, ReportLines)
        │
        ▼
[状态回写]
RunService.Action 落盘 store.SaveRun(player_id, state)
  └─ HTTP 响应 {"Success":..., "Message":..., "ActionResult":[...], "State":{...}}
        │
        ▼
[客户端回写]
Run 插件收到响应
  └─ 缓存最新 State 快照（只读语义：客户端不得改写）
  └─ context.Emit(KitchenEvents.RUN_CHANGED, snapshot)
        │
        ▼
[事件总线 / 域投影]
KitchenEventBus
  └─ Studio 插件收到 RUN_CHANGED → 摘出本域字段 → Emit(KitchenEvents.STUDIO_CHANGED, 投影)
  └─ 其余域插件同理（Orders / Staff / Market / Incidents 各自只在有变化时才被面板关心）
        │
        ▼
[UI 刷新]
PanelController 订阅本域事件 → 用 KitchenServices.<域> 的只读查询刷新 View
  └─ View 只做显示，不再解析服务器字段、不再拼协议
```

### 6.1 命令驱动同一条链路

`Client/Assets/Scripts/Kitchen/Command/KitchenCommandRunner.cs` 把 `命令 [字段=值 ...]` 解析为 `UiAction`，再交给 `IUiInputService.Dispatch`；UI 按钮也走 `IUiInputService.Dispatch`。因此：

- UI 能做的 = 命令能做的。
- 自动化回归、压测、回放、AI 自对局可以在没有 Panel / View 的情况下驱动一局。
- `UiAction` 新增公开字段时，必须同步进 `KitchenCommandRunner` 的参数映射表（见 [`分层与命令驱动.md`](分层与命令驱动.md)）。

### 6.2 心跳链路

心跳是独立的静默通道，不改变游戏状态：

```text
SessionPlugin / SessionReporter
  └─ ServerComm.SendHeartbeat(token, scene, panel, action, callback)
        └─ POST /api/heartbeat
              └─ Server/services/session.py::Heartbeat
                    ├─ 校验 token
                    ├─ 限流（单 IP 300/min）
                    ├─ 写在线留痕 data/online/<playerId>.json
                    └─ 返回 {Success, SessionOk, Throttled, ServerTime, HeartbeatTtl}
```

客户端定时 30 秒 + 操作/跳转/面板开关即时补发（去抖 1 秒）；心跳失败不打扰玩家，`SessionOk=false` 时停跳并广播会话失效事件。详见 [`服务器基座.md`](服务器基座.md)。

## 七、关键约定速查

- 数据层跑数据层，UI 层跑 UI 层；两层只经管理器与控制器交互。
- 面板不得 `new XxxPlugin(...)`，不得取 `KitchenPluginContext` / `KitchenPluginEngine`，不得自己拼协议 Body，不得解析服务器字段。
- 插件之间禁止直接引用；跨插件协作只经事件总线或服务接口。
- 服务器权威：客户端插件只发行动与展示快照，禁止本地改写服务器下发的 `JObject`。
- 事件名集中声明在 `KitchenEvents`，禁止裸字符串 `Emit("...")` / `Subscribe("...")`。
- 资源业务侧只走 `AssetLoader.*`；平台能力只走 `PlatformService.*`；本地存储优先走 `PlatformService.Storage*`。
- UI 落盘只走“一键生成”；字体只走 `UIFontProvider.Get()` / `UITheme.GetFont()`。
- 服务器改动先本地跑用例，再部署；客户端改动先桩编译 + 静态自检，再真编译。
